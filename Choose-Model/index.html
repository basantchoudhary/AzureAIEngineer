Choose the right model

The exam skill: choose an appropriate model for each task, including LLMs, small models, multimodal models and Foundry Tools. Exam questions test the category; model names are examples.

From CCA-F: the same idea as choosing Haiku, Sonnet or Opus: the cheapest model that passes your evaluation wins. Azure adds three things: a catalogue with many vendors, Foundry Tools that aren't LLMs at all, and a model router that chooses for you.

1 · The mind map: eight categories

Each branch is a category, with example models and the words in a question stem that point to it.

2 · The decision tree

Ask the questions in order. The first Yes wins. The order matters: a Foundry Tool beats any model, and a cheaper model beats a bigger one once it passes evaluation.

  1. 1

    Does a Foundry Tool already do this job (PII redaction, translating a document, reading an invoice, transcribing audio, offline extraction)?

    Yes →Use the Foundry ToolLanguage PII · Translator · Speech · Document IntelligenceDeterministic, cheaper, and the exam's 'least effort' answer. An LLM is the runner-up.
  2. 2

    Is the output something other than text: an image, a video, a voice, or vectors?

    Yes →Use a generation or embedding modelgpt-image-2 · sora-2 · gpt-realtime / Voice Live · text-embedding-3-largeMatch the model to the output type; chat models don't make images or vectors.
  3. 3

    Does the input include images, screenshots or charts that the model must read?

    Yes →Use a multimodal modelgpt-5 · gpt-4.1 · Phi-4-multimodalFor repeatable fields with confidence, Content Understanding beats a chat model.
  4. 4

    Does the task need multi-step reasoning: planning, maths, tricky code, or rules with many conditions?

    Yes →Use a reasoning modelo4-mini · o3 · gpt-5 (reasoning_effort)Slower, and reasoning tokens bill as output. No temperature; use reasoning_effort and max_output_tokens.
  5. 5

    Must it run on a device or offline?

    Yes →Use a small model on the edgePhi-4-mini (Foundry Local)Small open-weight models fit edge hardware; cloud-only models don't.
  6. 6

    Is the task simple, high-volume, and has a small model been proven accurate enough?

    Yes →Use a small modelgpt-5-mini · gpt-5-nano · gpt-4.1-miniThe cheapest model that passes your evaluation wins.
  7. 7

    Do prompts vary from trivial to hard, and you'd rather not choose per request?

    Yes →Use model routermodel-router: Balanced (default), Quality, or Cost modePicks a model per prompt. Smallest context window of its models; Global or Data Zone Standard only.
  8. 8

    Has prompting failed to get a consistent style or format, and you have hundreds of good examples?

    Yes →Fine-tune a modelgpt-4.1-mini (SFT, DPO) · o4-mini (RFT)Try prompts and RAG first. Fine-tuning teaches style and format, not fresh facts.
  9. ✓

    No to everything?

    Then →Otherwise: a general-purpose LLMgpt-5 · gpt-4.1 · Claude SonnetStart here, evaluate, then move down to a cheaper model if quality holds.

6 · Which model for developing agents

Recommendation: start a new prompt agent on a mid-size general-purpose model with strong tool calling (for example gpt-5-mini). Run the agent evaluators: task adherence, tool call accuracy, intent resolution. Move up (gpt-5, or a reasoning model) only if those fail, and move narrow subagents down to small models once they pass.

From CCA-F: the same split as Opus or Sonnet orchestrating and Haiku subagents doing narrow work. The model is the agent's brain; the tools, instructions and guardrails make it an agent, and they don't change with the model.

What makes a model good for agents, in order: reliable tool calling (right tool, valid arguments), instruction following over many turns, structured outputs, enough context for tool results, and latency per turn, since an agent makes several model calls per answer. Exam cue: a stem about an agent picking the wrong tool points to tool_choice, tool descriptions or a stronger model, not to temperature.

7 · The biggest cost levers

Is prompt caching the biggest lever? Usually not: not calling a model and choosing a smaller one come first, because they cut every token. Caching only discounts repeated input. For agents it's often the biggest single lever, because every turn resends the instructions, tools and history, so input dwarfs output.

Order of attack: avoid the call, then pick the smaller model, then trim output, then cache, then batch.

Exam traps: there's no "enable caching" switch on an Azure deployment: it's on by default for GPT-4o and newer. A prompt under 1,024 tokens never caches. Caching makes repeated input cheaper and faster; it never changes the answer.

8 · Model choice isn't deployment choice

Picking the model answers "what can do this job?". Picking the deployment type answers "where is it processed, and how do I pay?" (Global, Data Zone, Standard, Provisioned, Batch). A stem about residency or throughput is asking about the deployment, not the model. See D1.
